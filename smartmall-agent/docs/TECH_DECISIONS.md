# 技术选型记录（ADR）

每条记录格式：选择了什么 / 为什么不是另一种 / 代价。
这些决策在代码库里已是事实，记录它们是为了让后来的开发者知道"当时为什么这样做"。

## ADR-01：默认使用哈希向量，不是真实 embedding

**决定**：`HashEmbedding` 作为默认，配置真实 embedding 才换。

**理由**：
- 无密钥、无网络、确定性。这让"无 API Key 可跑全流程"成为默认而不是例外。
- 边界场景需要确定性输入：如果测试依赖语义相似度，换模型就可能改变测试结果，
  这比"测不到"更危险。
- 词面相似对于这个知识库（6 篇结构化文档）+这个问题集（关键词明确）已经够用；
  真正需要同义词覆盖的场景主要靠 BM25 分词承担。

**代价**：向量检索对同义改写无能为力，`"退差价"` 找不到 `"价格保护"`。
已在 README 和 EVALUATION 里如实声明。

## ADR-02：自写 BM25，不用 rank_bm25

**决定**：纯 Python 实现 Okapi BM25。

**理由**：
- rank_bm25 不支持中文分词，必须对接 jieba；自写可以把分词、停用词、k1/b 全部暴露出来，
  面试时解释参数含义时不用翻源码。
- BM25 本体就 60 行，引入一个库只是换了一个黑箱。

**代价**：没有向量化加速。当前语料规模下 BM25 延迟 0.03ms，接受。

## ADR-03：RRF 而非加权分数融合

**决定**：用 Reciprocal Rank Fusion，而不是 `α × vec_score + β × bm25_score`。

**理由**：
- 向量相似度（0–1 的余弦）和 BM25 分数（无上界的实数）量纲不同，
  线性加权前必须归一化，而 min-max / z-score 会随 query 变化而改变相对顺序，不稳定。
- RRF 只用排名，天然跨量纲可比，且对单路异常高分不敏感。
- k=60 是 RRF 原论文的常用取值，只有在大规模评测后才应该调整。

**代价**：RRF 对排名差异不敏感（第 1 名和第 2 名之间的分差消失了）。
如果某路检索的前几名质量差异很大，RRF 会欠补偿。

## ADR-04：LexicalReranker 不是 cross-encoder

**决定**：轻量词面覆盖率重排，不接 bge-reranker 等神经模型。

**理由**：
- 保持"无密钥、离线可测"的原则。cross-encoder 要加载几百 MB 的模型。
- 解决了一个具体问题：RRF 只看排名，当两块排名接近时无法区分
  "查询词全命中"和"只命中一个词"。覆盖率把前者提上来，有真实改善。

**代价**：对同义改写无能为力。实测 K=2 时 Precision 从 0.7917 提到 0.9167，
但 MRR（首位命中率）从 1.0 降到 0.9583——重排把综合好的块提前了，
但牺牲了个别"一击即中"的首位命中。这个 trade-off 在 EVALUATION 里有数据支撑。

## ADR-05：LangGraph 只管路由，不做子任务并发

**决定**：图结构用于意图路由（6 节点 + 条件边），每条路径最多 4 跳。

**理由**：
- 核心问题是**条件路由**：同一个问题根据意图走完全不同的分支，且分支固定。
  这正是图编排的适用场景。
- 没有"子任务动态图"的需求——不像 DRA 那样要在运行时生成 DAG。
  每条路径最多经过 4 个节点就到 END，没有回边，不需要 checkpointer。

**代价**：6 个节点的图用 if-else 也能写。使用 LangGraph 带来的额外价值是：
条件边声明式（一眼看出路由逻辑）、以及将来加 human-in-the-loop 时的 checkpointer 扩展点。

## ADR-06：业务规则在代码里，不在提示词里

**决定**：退货能不能退、订单能不能看，由 `business_rules.py` 的确定性代码判定，
LLM 输出不参与这个判定。

**理由**：
- 提示词约束是概率性的。模型在用户一句"但我真的很需要退"后改口是常见现象。
- 规则引擎的输出是可审计的（`ReturnEligibility` 有 `reasons` 列表）、可测试的（单元测试直接覆盖）。
- 权限校验（订单归属）同理：`assert_order_ownership` 是调用链上的硬门，不经过模型。

**代价**：规则变更时需要同时改代码和知识库文档，两者可能出现不一致。
约定：两者不一致时**以代码为准**（见 TOOLS_AND_BUSINESS_RULES）。

## ADR-07：SQLite 做会话持久化

**决定**：SQLite，不用 Redis 或 Postgres。

**理由**：单进程部署，会话只需要在重启后恢复，零运维。
会话读写有 asyncio.Lock，在进程内是并发安全的。

**代价**：多副本时 SQLite 不支持多写者。扩展路径是把 `SessionStore` 抽成 Protocol，
实现 Postgres 版。目前已知单进程限制，写在 ROADMAP。

## ADR-08：身份来自认证层，不来自聊天

**决定**：`user_id` 只从 `X-User-Id` 请求头读取（由网关/认证层注入），
用户在聊天中说"我是张三"永远不可信。

**理由**：这是越权防护的根本前提。`ToolContext.user_id` 来自 HTTP 层，
不是从意图槽位里抽出来的。两条防线：
1. 意图识别时槽位过滤掉 `user_id` 等身份字段；
2. 每次工具调用都用 session-bound 的 `ctx.user_id` 做归属校验。

**代价**：项目不做登录体系，假设网关存在。
这个假设在 README、SECURITY、API 文档里都如实标注了。

## ADR-10：没有使用 CrewAI

**决定**：不引入 CrewAI 或类似的多 Agent 框架。

**理由**：这是一个单 Agent + 条件路由的问题，不存在多智能体协作需求。
引入 CrewAI 只会在 LangGraph 之上再加一层框架，增加依赖深度、调试难度和文档厚度，
却得不到任何具体收益。
"展示会用多个框架"不是引入一个框架的充分理由。

**代价**：如果将来需要并行的多个 Agent 协作（如"商品 Agent"+"售后 Agent"分别处理再汇总），
需要重新评估。
