# RAG 深度问答

## Q1：你的 RAG 和"调一下 LangChain 的 RetrievalQA"有什么区别？

RetrievalQA 把"检索 + 塞上下文 + 生成"串起来，但它不管三件最容易出事的：

1. **召回了无关内容怎么办**。它会照样塞给模型，模型就"基于上下文"编一个答案。
   我在调模型之前加了相关性门槛（覆盖率 < 0.34 直接拒答）。
2. **模型编引用怎么办**。它不校验引用真实性。我做了 `validate_citations`：
   伪造的 chunk_id 剔除并记进 `dropped_citations`，剔除后一条真引用都不剩就降级为拒答。
3. **怎么知道换个检索方案是变好还是变坏**。它不带评测。
   我做了 24 条人工标注用例，4 种模式跑同一套，指标现场跑出来落盘。

还有一个工程层面的：它不管索引幂等。我的 `sma index` 重复执行写入量是 0，
文档变短时会先删旧块避免孤儿块——这些是实际运维里会咬人的地方。

## Q2：为什么不按固定长度切块？

看一个真实的例子，`aftersale_return_policy.md` 的结构：

```
## 不支持无理由退货的情况
定制类商品、已拆封的个人卫生用品…

## 退货运费
质量问题由平台承担，无理由退货由买家承担…
```

固定长度切会把前一节的后半段和后一节的前半段塞进同一个块。用户问"退货运费谁出"，
这个块被召回了——但块里一半内容在讲"哪些商品不能退"，模型很可能把两件事串起来答。

**召回正确 ≠ 回答正确**，噪声内容会污染生成。

所以按 Markdown 标题优先切：标题是作者标注的语义边界，
这是**免费的、人工质量的切分信号**，没有理由不用。
超长小节再按中文句末标点二次切分，带 64 字重叠防止答案正好落在切点上。

**追问：块的标题为什么要拼进正文？**

三个受益方：BM25（小节标题里"退货运费"这种词是高区分度检索词，不拼进去就搜不到）、
向量（标题词汇参与嵌入，提升主题相关性）、模型（知道这段话属于哪个主题，不容易跨主题串联）。

代价是重复的文档标题会略微拉低 BM25 的 IDF 区分度。6 篇文档的规模上可以忽略，
语料大了可以只拼小节标题。

## Q3：chunk_id 为什么是 `doc_id#seq` 而不是 UUID？

三个性质缺一不可：

1. **稳定可重建**——同样的内容 + 同样的 `chunk_size` 产生同样的 ID，这是索引幂等的前提（upsert 靠 ID 去重）；
2. **人类可读**——它会出现在引用里给人看，`aftersale_return_policy#2` 一眼知道出处，UUID 得反查；
3. **可反查**——引用校验要用它在本次检索结果里查回 Chunk 对象，取出 doc_id、title、snippet。

**追问：它随 chunk_size 变化，这不是问题吗？**

是问题，而且是我刻意处理过的：**评测集按文档粒度（doc_id）标注，不按块粒度**。
因为切块边界会随参数变化，块粒度的标注调完参就失效了，没法复用。

另一个影响是历史对话里的引用在改参后会指不回去。这个我没解——
当前规模下不值得为它引入 chunk_id 的版本映射表。

## Q4：默认的 HashEmbedding 是什么？它是语义向量吗？

**不是，这点我会主动说清楚。**

算法是经典的 hashing trick：文本切成中文单字和英文词，每个 token 用 sha256 映射到
256 维里的一个下标，按 TF 累加（带随机符号抵消哈希碰撞的系统性偏置），最后 L2 归一化。

它度量的是**词面重叠**。"价格保护"和"退差价"没有任何共享词，相似度接近 0，
而真语义模型能认出它们是同义。

**那它为什么是默认？** 约束驱动：需求要求"无密钥即可完整运行与测试"。
如果默认走真实 API，没密钥就跑不了任何测试，CI 也废了。
有了它，索引、相似度、RRF 融合、评测脚本、CI 整条链路离线可跑。

默认配置下，同义改写的检索能力主要由 **BM25 的 jieba 分词**承担
（jieba 会把"退差价"切出"差价"，和文档里的词对上）。
这也是默认 `SMA_RETRIEVAL_MODE=hybrid` 而不是 `vector` 的原因。

## Q5：换真实 embedding 要注意什么？

**必须 `sma index --full`，不能用增量。**

这是一个会静默出错的坑：增量模式只比对**内容哈希**，它**感知不到 embedding 模型变了**。
维度不同的话 Chroma 会报错（还算好）；维度恰好相同的话，新旧向量混在一个 collection 里，
算出的相似度完全无意义——而索引看起来是构建成功的。

我在 README、CHUNKING_AND_EMBEDDING、TROUBLESHOOTING 三处都写了这条警告。

**追问：ApiEmbedding 的实现里有什么容易漏的？**

按 index 重排返回结果：

```python
vectors = [item["embedding"] for item in sorted(data, key=lambda d: d.get("index", 0))]
```

OpenAI 兼容接口**不保证返回顺序与输入顺序一致**。不排序会导致向量和文本错配，
而且这种错误完全静默——索引构建成功，检索结果全是乱的。

还有返回数量校验：条数不等于输入条数直接抛错，不做"少了就补零"这种掩盖。

## Q6：为什么用 RRF 融合而不是加权分数相加？

量纲问题。向量相似度是 0–1 的余弦，BM25 分数是无上界的实数（可能是 2.3 也可能是 47）。
直接 `α·v + (1-α)·b` 等于让 BM25 单方面主导。

先归一化？min-max 和 z-score 都依赖**当前这批候选的分布**。
同一个块在不同 query 下，因为同批候选的最高分不同，归一化后的分数会不同——
相对顺序随查询漂移，不稳定也没法调参。

RRF 只用排名：`score(d) = Σ_r 1/(k + rank_r(d))`。
跨量纲天然可比，对单路异常高分不敏感（给了离谱高分也只是"排名第 1"，贡献 1/61），
而且没有权重要调。

**追问：k=60 是什么作用？**

压缩头部差距。排名 1 贡献 1/61 ≈ 0.0164，排名 2 贡献 1/62 ≈ 0.0161，差距只有 2%。
这意味着"两路都排在前几名"比"一路排第 1、另一路没召回"更有优势——正是融合想要的效果。
k 调小会让第一名权重陡增，退化成"谁家第一名说话算"。

**追问：RRF 的代价是什么？**

丢弃了分数里的置信度信息。"相似度 0.95 的第一名"和"0.31 的第一名"在 RRF 眼里完全一样。
所以我额外补了 `min_score` 过滤和相关性门槛——它们不是冗余设计，
是在补 RRF 主动放弃的那部分信息。

另外一个实际的坑：**`min_score` 的量级随模式变化**。RRF 分数约 0.016 量级，
向量相似度是 0–1 量级。把向量模式的阈值直接用在 hybrid 上会过滤掉全部候选。

## Q7：BM25 自己实现，有哪些细节容易写错？

**① IDF 要防负值。** 教科书公式 `log((N-df+0.5)/(df+0.5))` 在 `df > N/2` 时是**负数**——
即"在超过一半文档里出现的词，命中它反而扣分"。我的语料只有 28 个块，
"退货"这个词可能出现在一半的块里，负 IDF 会把排序彻底搅乱。所以用 `log(1 + ...)` 保证恒正。

**② 停用词要含场景词。** 不只是"的/了/是"，还要有"请问/一下/怎么/可以"。
"请问一下怎么退货"分词后前三个词会出现在几乎每条用户问题里，
而它们在文档里几乎不出现——IDF 很高，反而抢走权重。

**③ 排序必须有 tie-break。**

```python
scores.sort(key=lambda x: (-x[1], self.chunks[x[0]].chunk_id))
```

不加的话，同样的输入会得到不同的顺序，评测结果就不可复现了。小语料上同分很常见。

**④ k1 和 b 的含义要说得出来。** k1 控制词频饱和速度（词出现 10 次不该比 1 次得分高 10 倍）；
b 控制文档长度归一化强度。我的块长度相对均匀（都在 chunk_size 附近），
所以 b=0.75 的默认值合适；块长差异大的语料应该调高 b。

## Q8：BM25 索引是从哪里建的？

**从 Chroma 取全量块重建**，不重读磁盘文件。

这是故意的：两个索引共用同一份语料，**不可能出现"向量里有、BM25 里没有"的不一致**。

代价讲清楚：常驻内存，进程重启要重建。28 个块的重建成本可忽略；
语料上千后内存占用和启动时间都会成问题，那时该换持久化倒排索引——已记在 ROADMAP。

## Q9：重排带来了什么？代价是什么？

实测数据（12 条用例，hash embedding）：

| K | 指标 | hybrid | hybrid_rerank |
|---|------|--------|---------------|
| 2 | Precision | 0.7917 | **0.9167**（+15.8%） |
| 4 | Precision | 0.6250 | **0.7639**（+22.2%） |
| 2 | MRR | 1.0 | 0.9583（**−4.2%**） |
| 1 | 三项全部 | 0.9583/1.0/1.0 | 0.875/0.9167/0.9167（**全降**） |

**收益是 Precision，随 K 增大而增大**——K 越大进入上下文的无关块越多，压下去的价值越明显。

**代价是 MRR 降 4.2%**。12 条用例里 MRR 从 1.0 降到 0.9583，
意味着**有一条用例的首个正确文档从第 1 位掉到了第 2 位**（1/2 对 12 取平均正好 −0.0417）。

这不是噪声，是可解释的机制性缺陷：**词面覆盖率会高估"词多但主题偏"的块**。
一个块恰好包含问题里的多个词但整体在讲另一件事，覆盖率会把它推上来。
cross-encoder 不会犯这个错，因为它看语义匹配。

所以 **K=1 时重排是净亏损的**，默认配置也没有开它。

**追问：为什么重排打分里要保留原排名？**

```python
base = 1.0 / (10 + item.rank)
scored.append((coverage + position_bonus + title_bonus + base, item))
```

没有 `base` 项，重排完全由词面覆盖率决定，等于把向量检索的贡献全部丢掉——那还不如直接用 BM25。
`1/(10+rank)` 的量级约 0.03–0.09，相当于"覆盖率差 5% 以内时听召回阶段的"。

常数 10 比 RRF 的 60 小得多，因为这里候选只有 10 个，需要更明显的排名区分度。

## Q10：召回宽度怎么定的？

每路召回 `candidate_k=10`，融合后截断到 `top_k=4`。

**召回要宽，排序才收窄。** 如果每路只召回 4 个，融合时信息量只有 8 条（且高度重叠），
RRF 的互补效应发挥不出来。把 candidate_k 开大的成本只是 BM25 多算几条和一点融合开销
（实测 p50 < 1ms），收益是融合质量。

## Q11：上下文拼装有什么讲究？

```python
block = f"[{item.chunk_id}] 《{item.chunk.title}》\n{item.chunk.content.strip()}\n"
if total + len(block) > max_chars:
    break
```

两点：

1. **chunk_id 必须出现在上下文里**，否则模型无法引用，引用校验也无从校验。
2. **整块纳入或整块丢弃，绝不截半块。** 截半块会让 chunk_id 与实际内容错配——
   引用指向的片段和模型看到的不是一回事，校验就失去意义了。

## Q12：怎么防止模型编答案？

三层，其中两层是**确定性**的：

| 层 | 机制 | 性质 |
|----|------|------|
| 1 | 相关性门槛：覆盖率 < 0.34 直接拒答，**不调模型** | 确定性 |
| 2 | 提示词：只能引用实际出现的编号，片段不足就 no_answer | 概率性 |
| 3 | 引用校验：伪造 ID 剔除，全假则降级拒答 | 确定性 |

第 3 层的降级逻辑值得说：如果剔除后一条真引用都不剩，而状态是 `answered`，
就强制降级为 `no_answer`。理由很直接——**"声称有依据但一条真引用都没有"比"说不知道"更危险**。

还有一条辅助：`find_unsupported_numbers` 检测回答里出现但上下文里找不到的数字。
这个**只告警不拦截**（可能是合理的单位换算），但日志里频繁出现就说明提示词约束不够。

## Q13：排查"为什么答成这样"你怎么做？

看 `RetrievalTrace`，请求带 `include_trace: true` 就能拿到：

```
vector_candidates → bm25_candidates → fused_order → reranked_order → final_chunk_ids → context_chars
```

它能一眼分辨三类问题，而这三类的修法完全不同：

| trace 表现 | 问题类型 | 修法 |
|-----------|---------|------|
| 正确文档不在任何 candidates 里 | **检索**问题 | 改切块 / 换 embedding / 补文档 |
| 在 `fused_order` 里但不在 `final_chunk_ids` 里 | **截断**问题 | 调大 `context_max_chars` 或调小 `chunk_size` |
| 在 `final_chunk_ids` 里但回答没用 | **生成**问题 | 改提示词 / 降温度 |

另外 `retriever` 字段记录了来源（`vector` / `bm25` / `vector+bm25`），
能看出某块是两路都召回还是只有一路——这个信息在判断"要不要调融合"时很有用。

## Q14：如果让你换成 cross-encoder 重排，你会怎么做？

接口已经留好了（`Reranker` 抽象），实现大概 10 行。但换之前要想清楚四件事：

1. **延迟**：每个候选过一次模型。candidate_k=10 就是 10 次前向推理，
   本地 CPU 上 bge-reranker-v2-m3 大约几百毫秒。必须实测后重新定 candidate_k。
2. **同步阻塞**：`CrossEncoder.predict` 是同步的，直接在 async 节点里调会阻塞事件循环。
   要包 `asyncio.to_thread` 或走独立推理服务。
3. **依赖体积**：sentence-transformers + torch 会让镜像从几百 MB 涨到几个 GB。
   这是当前没默认引入的实际原因之一。
4. **必须重跑评测**：不要凭"cross-encoder 肯定更好"直接上。
   在短文本、强词面匹配的客服场景下，它未必能赢过 BM25 + 词面重排的组合。

**我没有实际跑过 cross-encoder**，所以文档里也没有任何它的性能数字——
只有接口示例代码，并明确标注"未实现未实测"。
