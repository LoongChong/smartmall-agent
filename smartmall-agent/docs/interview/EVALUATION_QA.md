# 评测与质量问答

## Q1：你怎么知道你的检索方案是好的？

我不知道它"好"，我只知道**在我的评测集和语料上，四种模式的相对表现是什么**。
这个区分很重要，我不会说"我的混合检索效果很好"。

具体做法：24 条人工标注用例（12 条检索 + 12 条行为），4 种检索模式跑同一套，
指标现场跑出来落盘到 `docs/benchmarks/`。

```bash
uv run sma eval                        # K=4 的四模式对比
uv run python scripts/eval_sweep.py    # K=1..4 扫描
```

实测（hash embedding，6 篇文档，12 条检索用例）：

| 模式 | Recall@4 | MRR | Precision@4 | p50 |
|------|----------|-----|-------------|-----|
| vector | 1.0 | 1.0 | 0.5069 | 0.57 ms |
| bm25 | 1.0 | 0.9583 | 0.7083 | 0.04 ms |
| hybrid | 1.0 | 1.0 | 0.6250 | 0.59 ms |
| hybrid_rerank | 1.0 | 0.9583 | 0.7639 | 1.66 ms |

## Q2：Recall 全是 1.0，是不是说明方案完美？

不是，**这是天花板效应**，我在每个引用这张表的地方都标注了。

只有 6 篇文档，命中正确文档太容易了。K≥2 时四种模式的 Recall 全部到顶，
**这个指标在这个语料上已经失去区分能力**。

区分度在哪里：

- **K=1 的 Recall**：vector/hybrid 0.9583，bm25/hybrid_rerank 0.875；
- **各 K 的 Precision**：K=4 时从 0.5069（vector）到 0.7639（hybrid_rerank）。

这也是为什么我写了 `eval_sweep.py` 做 K=1..4 扫描——
只看 K=4 一个点会得出"四种模式一样好"的错误结论。

**所以要真正调这套参数，前提是把语料扩到 50+ 篇、评测集扩到 100+ 条。**
这是 ROADMAP 里 P1 的第一项，因为它是所有调参工作的前提。

## Q3：指标为什么按文档粒度算，不按块粒度？

因为**切块边界会随 `chunk_size` 变化**。

如果按 chunk_id 标注期望答案，那么每次调 `chunk_size`，所有标注都失效——
而调切块参数恰恰是检索优化里最常做的事。按 doc_id 标注的话，标注可以跨参数复用。

代价是粒度变粗：同一文档里"召回了正确的块"和"召回了错误的块"算一样。
在 6 篇文档的规模上这个损失可以接受；语料大了应该两个粒度都算。

```python
def dedup_docs(hits: list[RetrievedChunk]) -> list[str]:
    """把块级检索结果折叠成文档级列表，保持顺序。"""
    return list(dict.fromkeys(h.chunk.doc_id for h in hits))
```

## Q4：三个指标分别说明什么？什么时候该看哪个？

| 指标 | 定义 | 回答什么问题 |
|------|------|-------------|
| Recall@K | 前 K 个结果覆盖的期望文档 / 期望文档总数 | **该找到的找到了吗** |
| MRR | 1 / 第一个命中期望文档的排名 | **最相关的排得够前吗** |
| Precision@K | 前 K 个结果里命中期望文档的比例 | **塞给模型的上下文有多少是噪声** |

什么时候看哪个：

- 只展示一条答案（如语音助手）→ 看 **MRR**；
- 要把 top_k 都喂给模型 → 看 **Precision**（噪声会污染生成）；
- 判断"是不是根本没召回到" → 看 **Recall**。

我的默认配置 `top_k=4` 把 4 个块都喂给模型，所以 Precision 是我最关心的。
这也是为什么重排的 Precision 收益（+22% @K=4）在我这里是有意义的。

## Q5：用例是怎么来的？让模型生成的吗？

**人工标注的。** 让模型生成用例等于用模型考模型——
模型生成的问题会倾向于用文档里的原词，于是检索看起来特别准，而这正是要测的东西。

12 条检索用例覆盖的类型：

| 类型 | 例子 |
|------|------|
| 商品属性 | "星云 Pro 14 的屏幕刷新率是多少" |
| 单文档多属性 | "清风 S3 耳机的降噪深度和续航分别是多少" |
| 政策细节 | "7 天无理由退货是从什么时候开始算" |
| 跨文档 | "笔记本电脑保修几年，电池也一样吗"（保修条款 + 商品页都提到） |
| 口语化/同义 | 刻意用和文档不同的说法 |
| 歧义 | 需要澄清的问法 |

12 条行为用例覆盖：拒答、澄清、工具调用、越权、prompt injection、高风险转人工。

## Q6：讲一个评测真正发现了缺陷的例子。

有两条，而且这是我最想讲的部分。

**`b01`：问"你们公司 CEO 是谁"，期望 `no_answer`，实际是 `answered`。**

原因：向量检索永远返回 top_k 个结果，哪怕全不相关。模型拿到了售后政策的片段，
就"基于上下文"编了一个答案。

**`b10`：prompt injection 输入，期望 `escalated`，实际被当普通问题正常回答。**

原因：当时只在提示词里写了"遇到注入请归类为 out_of_scope"，这是概率性的，没拦住。

**处理方式是改代码，不是改评测期望。** 新建了 `agent/guards.py`：

- `relevance_guard`：覆盖率 < 0.34 直接拒答，**在调模型之前**；
- `detect_injection`：19 条模式确定性匹配，命中即短路。

修完 12/12 通过。

这件事说明的是评测集的真正价值：**它不是用来产出好看数字的，是用来发现缺陷的。**
如果我当时把期望值改成 `answered`，就会得到一个"100% 通过"的评测集和两个真实漏洞。

## Q7：还有别的质量机制发现过问题吗？

有。引用校验机制在开发期抓到过 mock LLM 的 bug。

mock 模型要返回引用列表，它的实现是从消息里扫 ID 模式。结果它把**系统提示词里的占位符**
`ev_xxxxxxxx` 当成了真 ID 输出。引用校验发现这个 ID 不在检索结果里，剔除，
剔除后一条不剩，状态降级为 `no_answer`。

修的是 mock 的正则（改成严格的 `\bev_[0-9a-f]{16}\b` 且只扫 user 消息），
但**机制生效这件事本身值得记下来**——那套校验不是摆设。

## Q8：mock 模型下的评测有什么意义？它不是假的吗？

要分清测什么。

**mock 下有效的**：

- 检索指标（Recall/MRR/Precision）——检索完全不经过 LLM，这些数字和模型无关；
- 路由正确性——意图路由的分支逻辑；
- 确定性防护——注入短路、鉴权、规则引擎、引用校验的**机制**是否生效；
- 状态流转——降级、拒答、转人工的路径是否正确。

**mock 下无效的**：

- 回答的语言质量；
- 意图识别的准确率（mock 是关键词匹配的）；
- 提示词约束的实际效果（概率性防护）；
- 延迟（mock 没有网络 I/O）。

所以我在 EVALUATION 文档里明确写了"mock 通过率不代表真实模型下的表现"，
也绝不会说"行为用例 12/12 通过，所以 Agent 质量很好"。
正确的说法是"**Agent 的分支逻辑和确定性防护机制 12/12 符合设计**"。

## Q9：你的延迟数字能用吗？

**不能当生产指标。** p50 0.04–1.66ms 这个量级一看就知道是纯本地内存操作：
没有网络调用，没有真实 embedding 的 API 往返（那是几十到几百毫秒），
没有 LLM 调用（那是几百毫秒到几秒）。

它唯一的用处是**横向比较**：BM25 比向量快一个数量级（0.04 vs 0.57ms，
因为向量路要算 query embedding）；重排增加约 1ms（2.8×）。

这些相对关系是有意义的，绝对值没有意义。

我在文档里写得很直白：延迟是纯本地计算，不能当生产指标。

## Q10：`percentile` 为什么用最近邻插值而不是线性插值？

```python
def percentile(values: list[float], p: float) -> float:
    ordered = sorted(values)
    idx = min(len(ordered) - 1, max(0, round((len(ordered) - 1) * p)))
    return round(ordered[idx], 2)
```

样本量小的时候，线性插值会产生**误导性的"精确值"**。
12 个样本算 p95，线性插值会给出一个两个实际观测值之间的数——
看起来很精确，实际上是插出来的，样本量根本不支持这个精度。

最近邻返回的是一个**真实观测到的值**，更诚实。

## Q11：评测结果怎么保证可复现？

四件事：

1. **所有排序都有 tie-break**。BM25、RRF、重排都是 `key=(-score, chunk_id)`。
   不加的话同样输入会得到不同顺序，小语料上同分很常见。
2. **固定时间基准**。`mock_data.NOW` 是模块级常量。用 `datetime.now()` 的话，
   "签收 5 天的订单能退货"这条断言会在 3 天后失败。
3. **mock LLM 是确定性的**（关键词匹配，不是随机）。
4. **环境信息一并记录**：

```json
"environment": {"platform": "macOS-27.0.1-arm64", "python": "3.11.16",
  "llm_provider": "mock", "embedding_provider": "hash", "chunk_size": 320, "top_k": 4}
```

这一条是最容易忽略的。同一个指标在不同 `chunk_size` 或不同 embedding 下
完全不可比，不记环境的数字等于没有数字。

## Q12：你的测试覆盖了什么？90% 覆盖率说明什么？

174 个离线测试，覆盖率 90%。但我更关心覆盖了什么，而不是百分比：

| 文件 | 覆盖什么 |
|------|---------|
| `test_knowledge.py` | frontmatter 解析、切块、**索引幂等**、增量更新、**孤儿块清理** |
| `test_retrieval.py` | BM25 打分、RRF 融合、重排、上下文拼装、trace |
| `test_agent.py` | 意图路由、**注入短路**、**相关性门槛**、**引用校验降级** |
| `test_tools.py` | 五段式各段、**越权**、**高风险拦截**、**幂等**、业务规则 |
| `test_api.py` | 路由、**管理员鉴权**、**会话隔离**、错误响应、**密钥脱敏** |
| `test_http_clients.py` | MockTransport：重试、超时、**错误分类** |

加粗的是失败路径和安全路径——**这些比 happy path 重要得多**。
90% 这个数字本身说明不了什么，一堆只测 getter 的测试也能刷到 90%。

**追问：外部调用为什么用 MockTransport 而不是 mock 掉整个客户端类？**

因为 mock 掉整个类就测不到真实的请求构造逻辑。

这条有实际价值：`test_http_clients.py` 暴露出 DeepSeek 适配器的一个真实缺陷——
注入自定义 client 时 `base_url` 和 Authorization header 被忽略了
（报错是 "unknown url type: '/search'"）。如果 mock 掉整个类，这个 bug 永远测不出来。

修复是改用绝对 endpoint URL + 每请求下发 headers。

## Q13：集成测试为什么默认跳过？

```toml
addopts = "-q --strict-markers -m 'not integration'"
```

因为它们会**真的调 API、真的花钱**。默认跑全量会让 `pytest` 在没有密钥时失败、
有密钥时产生费用。

`--strict-markers` 的作用也值得说：打错 marker 名字会直接报错，
而不是静默创建一个新 marker——那样 `-m integration` 就筛不到，
集成测试会在 CI 里被**意外执行**。

**但我必须如实说：这 4 个集成测试从未被实际执行过。** 我没有可用的 DeepSeek 密钥。
代码写好了，验收结论里标的是"未验证"，而不是"通过"。

**所以这个项目的文档里不出现任何真实模型下的准确率、延迟或质量数字。**

## Q14：如果给你真实密钥和一周时间，你会怎么做评测？

按优先级：

1. **先扩语料和用例**（50+ 篇文档，100+ 条用例）。
   当前的天花板效应让大部分实验测不出差异，不先解决这个，后面的实验都是浪费。
2. **跑集成测试，记录真实指标**，更新 EVALUATION 文档。
3. **重跑四模式对比**。换真实 embedding 后两路的互补性会变强，
   我预期 hybrid 相对单路的优势会比现在明显——但这是预期，不是结论，要跑出来才算。
4. **接 cross-encoder 重排并对比**。重点看它能不能解掉词面重排那个 MRR −4.2% 的机制性缺陷。
5. **加端到端质量评测**：不只看检索指标，还要人工标注回答质量
   （有依据/无依据/拒答是否恰当）。这一层目前完全没有。
6. **做一次压测**，拿到并发下的 p95/p99。当前完全没有并发数据。

第 5 项是当前最大的空白：我测了"检索对不对"和"分支走对没有"，
但"回答写得好不好"这件事只有在真实模型下才有意义，所以现在完全没测。

## Q15：你怎么防止评测集本身出问题？

几条实践：

1. **标注基于文档实际内容**，不凭印象写期望。写用例时是对着文档逐条确认的。
2. **用例失败时默认假设是代码错**，不是期望错。AGENTS.md 里把这条写成了规则。
3. **CI 里跑评测**。`sma eval` 是 CI 的一个步骤，任何改动导致行为用例回归都会被挡下。
4. **加新功能必须加用例**。尤其是加意图——新意图最容易**抢走已有意图的分类**，
   比如新增"修改收货地址"会抢走一部分"订单查询"。只有评测集能发现这个。

还有一条是我没做但应该做的：**评测集本身没有版本化的变更记录**。
现在改了用例只能从 git log 看，应该有一份变更说明解释"为什么改了这条期望"——
否则将来有人改期望值来让测试通过，审查时很难发现。
